# SteamSell

Telegram-магазин на Python: aiogram 3, FastAPI, PostgreSQL, SQLAlchemy/Alembic та Redis. Інтерфейс покупця українською й російською, керування магазином — через `/admin` у приватному чаті.

## Можливості

- Каталог і новинки з пагінацією, фото, описом та ручним порядком товарів на головній.
- Monobank merchant acquiring: окремі рахунки, ECDSA-перевірка webhook, перевірка суми/UAH/reference, захист від повторної обробки, періодична звірка статусів.
- Автоматична видача Steam-даних, історія покупок зі знімком назви й ціни. Товар продається повторно; приховування та soft delete не забирають попередні покупки.
- Gmail OAuth для кожного товару, отримання свіжого Steam Guard-коду, перевірка покупця, ліміти запитів і журнал без кодів та токенів.
- Покрокове додавання товару, редагування окремих полів, підтвердження змін, користувачі, замовлення, статистика, налаштування та розсилки з двома підтвердженнями.
- Шифрування Steam-даних, Gmail refresh tokens і змінюваного Monobank-токена через Fernet. Чернетки секретів у Redis також зашифровані.
- Docker Compose, міграція бази, щоденний backup, перевірка `/health`, CI та автоматичні тести.

## Запуск

Для **Railway власний домен і reverse proxy не потрібні** — використовуйте надану хостингом HTTPS-адресу. Інструкція нижче. Один екземпляр `app` запускає polling Telegram, HTTP endpoints та worker. Не збільшуйте кількість workers/replicas без винесення polling і черги в окремі процеси.

### Railway — без купівлі домену

1. Створіть Railway project і додайте сервіс із цим GitHub-репозиторієм, **Postgres** та **Redis**. Код має бути завантажений у GitHub. `railway.json` налаштовує Docker build, міграції перед запуском, один екземпляр та `/health`.
2. У сервісі бота відкрийте **Variables → Raw Editor** і вставте вміст [.env.railway.example](.env.railway.example). Локальний `.env` для Railway не потрібний.
3. Посилання `DATABASE_URL=${{Postgres.DATABASE_URL}}` і `REDIS_URL=${{Redis.REDIS_URL}}` мають відповідати назвам ваших сервісів. Пароль бази окремо створювати або копіювати не потрібно. Стандартний PostgreSQL URL програма автоматично адаптує для asyncpg.
4. Заповніть власні значення:

   | Змінна | Що вказати |
   |---|---|
   | `BOT_TOKEN` | Токен бота від BotFather |
   | `ADMIN_ID` | Ваш числовий Telegram ID |
   | `ENCRYPTION_KEY` | Згенерований ключ Fernet; команда нижче |
   | `MONO_TOKEN` | Merchant acquiring token Monobank |
   | `GOOGLE_CLIENT_ID` | OAuth client ID типу Web application |
   | `GOOGLE_CLIENT_SECRET` | Secret цього Google OAuth client |
   | `SUPPORT_USERNAME` | Ваш Telegram username без `@` |

5. У сервісі бота: **Settings → Networking → Public Networking → Generate Domain**, target port **8000**. Railway надасть адресу на зразок `https://steamsell-production.up.railway.app`. Її бере змінна `RAILWAY_PUBLIC_DOMAIN`; `PUBLIC_BASE_URL` можна взагалі не задавати. Якщо раніше скопіювали `https://shop.example.com`, видаліть цю змінну — явно задана адреса має пріоритет.
6. У Google Cloud → OAuth client → **Authorized redirect URIs** додайте `https://ВАША-АДРЕСА.up.railway.app/oauth/gmail/callback`. Використовуйте саме адресу з Railway. Власний придбаний домен не потрібен; налаштування consent screen/дозволів Google залишаються обов'язковими.
7. Застосуйте Variables і виконайте **Deploy/Redeploy**. Міграції запускаються автоматично. Якщо перша спроба відбулась до заповнення ключів чи генерації адреси, повторіть deploy після налаштувань.
8. Перевірте `https://ВАША-АДРЕСА.up.railway.app/health`, потім `/start` і `/admin` у Telegram. Залиште один replica та вимкніть Serverless/App Sleeping, якщо цей режим увімкнено: бот має постійно отримувати оновлення і перевіряти платежі.

`PORT` використовується програмою автоматично; у прикладі задано 8000. HTTPS завершується на Railway, сертифікати чи Caddy налаштовувати не потрібно. `compose.yaml` на Railway не запускається: Postgres і Redis створюються окремими сервісами. Сервіс `backup` із Compose також **не запускається** — налаштуйте резервні копії PostgreSQL окремо в Railway та перевірте відновлення.

Генерація ключа локально:

```sh
uv run python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Скопіюйте ключ у Variables і збережіть захищену резервну копію. Не генеруйте новий ключ при кожному deploy.

Документація: [адреси Railway](https://docs.railway.com/networking/domains/working-with-domains), [змінні Railway](https://docs.railway.com/variables/reference), [pre-deploy міграції](https://docs.railway.com/deployments/pre-deploy-command).

### Власний сервер із Docker Compose

Для цього варіанта потрібен сервер із Docker Compose. Домен і HTTPS reverse proxy потрібні тільки для Gmail OAuth або Monobank acquiring webhook.

#### Ubuntu 24.04: запуск для клієнта

На чистому VPS з Ubuntu 24.04 клієнт завантажує репозиторій і виконує одну команду:

```sh
git clone https://github.com/USERNAME/SteamSell.git && cd SteamSell
sudo bash deploy/install-ubuntu.sh
```

Скрипт встановлює Docker, створює `.env` із новими локальними паролем БД та ключем шифрування
і не запускає бот, доки клієнт не внесе свої секрети. Далі:

```sh
nano .env
docker compose up -d --build
```

Клієнт має зберегти свій `ENCRYPTION_KEY` окремо: він потрібен для відновлення даних із backup.
Не передавайте клієнту чужі `.env`, `backups/` або Docker volumes.
Якщо використовується лише оплата на картку (`MANUAL_CARD`), домен для запуску бота не потрібен.
Для Gmail OAuth потрібна постійна HTTPS-адреса в `PUBLIC_BASE_URL`.

1. Скопіюйте `.env.example` у `.env`.
2. Заповніть `BOT_TOKEN` від BotFather і свій числовий `ADMIN_ID`. Вкажіть `SUPPORT_USERNAME` без `@`.
3. Створіть ключ: `uv run python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`. Запишіть результат у `ENCRYPTION_KEY`. Збережіть окрему захищену копію ключа: без нього база не розшифровується. Не змінюйте ключ без міграції зашифрованих даних.
4. Задайте сильний `POSTGRES_PASSWORD` і той самий пароль у `DATABASE_URL` (спецсимволи в URL потрібно percent-encode).
5. Додайте `MONO_TOKEN` еквайрингу, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `PUBLIC_BASE_URL=https://ваш-домен`.
6. Виконайте `docker compose up -d --build`. Сервіс `migrate` застосує Alembic перед стартом бота.
7. Налаштуйте HTTPS proxy на `127.0.0.1:8000`. Приклад для Caddy у `deploy/Caddyfile`. Не записуйте query string OAuth callback в access logs.
8. Відкрийте `/start`, оберіть мову. З акаунта адміністратора відкрийте `/admin` і додайте товар.

Команди перевірки:

```sh
docker compose ps
docker compose logs --tail=100 app
curl https://ваш-домен/health
```

База та Redis не публікують порти назовні. `.env` не потрапляє в Git або Docker image. Обмежте доступ до `.env`, Docker host, Redis і директорії backups.

## Monobank
Адміністратори: `ADMIN_ID` — основний адміністратор і отримувач сповіщень.
Додаткових адміністраторів головний адміністратор може призначати та прибирати в адмін-панелі: «Користувачі» → профіль користувача. Вони мають усі функції адмін-панелі, крім призначення інших адміністраторів. Роль зберігається в базі даних і застосовується одразу.
Параметр `ADMIN_IDS=1042869230,123456789` у `.env` також підтримується для сумісності, але керувати такими записами через панель не можна.


Для переказів на картку встановіть `MANUAL_CARD` (16 цифр) та персональний `MONO_TOKEN` у `.env`.
Бот визначає гривневий рахунок за маскою картки через `/personal/client-info` і перевіряє виписку
кнопкою «Перевірити платіж», не частіше ніж раз на 65 секунд. Покупець переказує точну суму
після створення замовлення; коментар не перевіряється. Видача відбувається лише за позитивним
гривневим надходженням із відповідними сумою й часом, включно з `hold=true`.
Товар може бути виданий до остаточного завершення операції банком; автоматичного відкликання
доступу при скасуванні операції немає. ID використаної транзакції
зберігається в `payment_events`; унікальний digest рахунку та ID запобігає повторному зарахуванню.
Кнопка перевіряє конкретне замовлення: перший невикористаний збіг у виписці зараховується йому,
навіть якщо інші замовлення мають таку саму суму. Запис використаної транзакції та оплата атомарні.
Сума й час не ідентифікують відправника: сторонній переказ на таку ж суму також може збігтися.
Порожній `MANUAL_CARD` залишає режим merchant acquiring. Після зміни конфігурації перезберіть
контейнери командою `docker compose up -d --build`; міграції застосовуються сервісом migrate.
Замовлення на перекази перевіряються до 30 днів; старіші надходження потребують окремого розгляду.


Потрібен **merchant acquiring token**, а не токен персональної виписки. Тестовий токен можна отримати на порталі Monobank. Використовуйте тестове середовище перед увімкненням реальних продажів.

Рахунок передає суму цілим числом копійок, валюту 980, внутрішній ID замовлення як `reference` і callback `PUBLIC_BASE_URL/webhooks/monobank`. Підпис перевіряється на незмінених байтах тіла через public key провайдера. Лише підтверджений `success` із відповідними реквізитами надає доступ. Зміна merchant token в адмінці заборонена, доки є замовлення `waiting_payment`.

Звірка статусів працює приблизно щохвилини для рахунків старше двох хвилин. Якщо відповідь створення рахунку загубилася, підписаний webhook може зв'язати рахунок із замовленням через `reference`. Видача відбувається окремим worker після фіксації платежу в базі.

Джерело: [офіційна документація Monobank acquiring](https://api.monobank.ua/docs/acquiring.html).

## DeepSeek: перевірка скриншотів оплати

У `.env` задайте `DEEPSEEK_API_KEY`, `DEEPSEEK_VISION_MODEL=deepseek-v4-flash-vision-exp`
і `DEEPSEEK_TIMEOUT=60`. В адмінці відкрийте «Керування картками», додайте одну або дві
активні картки, потім у «Режим оплати» виберіть «DeepSeek-скрін». Режим змінюється для всього
магазину й застосовується тільки до нових замовлень.

Покупець бачить активні картки, оплачує точну суму та надсилає квитанцію як фото. Бот приймає
JPEG, PNG, GIF або WebP до 8 MB, зберігає унікальний SHA-256 скріну й не дозволяє повторно
використати той самий файл. DeepSeek перевіряє видимі суму, успішний статус, час і останні чотири
цифри картки отримувача; IBAN ігнорується. Для автоматичного підтвердження потрібна впевненість
щонайменше 90%. Помилки, нечіткі або неповні скріни надходять усім адміністраторам із кнопками
підтвердження та відхилення. Картки старого замовлення зберігаються в його зашифрованому знімку,
тому їх можна замінювати або видаляти в адмінці без зміни вже створених оплат.

Перевірка зображення моделлю не доводить фактичне надходження грошей: якісно підроблений скрін
може пройти аналіз. Для фінансової гарантії використовуйте режим Monobank API або звіряйте
сумнівні платежі вручну за банківською випискою.

Документація моделі: [DeepSeek Vision](https://api-docs.deepseek.com/guides/vision/).

## Підключення Gmail

1. У Google Cloud увімкніть Gmail API, налаштуйте OAuth consent screen та OAuth client типу **Web application**.
2. Додайте точний redirect URI: `https://ваш-домен/oauth/gmail/callback`.
3. Налаштуйте доступ до застосунку для потрібних Gmail-скриньок. Для довготривалої роботи врахуйте вимоги Google до публікації/верифікації застосунку зі scope `gmail.readonly`; тестовий OAuth режим має обмеження строку життя refresh tokens.
4. У майстрі товару на кроці Gmail натисніть «Підключити Gmail», авторизуйте потрібну скриньку в Google, поверніться в Telegram і натисніть «Перевірити підключення».
5. Перевірте показану email-адресу й збережіть товар. Перепідключення доступне в картці товару → Gmail OAuth; воно потребує підтвердження.

Пароль Gmail не використовується. OAuth state одноразовий, живе 10 хвилин; результат прив'язаний до конкретної спроби підключення, зашифрований і живе 30 хвилин до збереження.

Парсер `app/gmail.py` шукає login-листи від `noreply@steampowered.com` із зазначеним Steam login, новіші за оплату й `CODE_MAX_AGE` (типово 180 секунд). Коди відновлення пароля не видаються. Один і той самий лист повторно тому самому покупцю не видається. Ліміт: 30 секунд між запитами як для користувача, так і для спільного товару; максимум 10 спроб за 10 хвилин.

Формат теми й тіла Steam-листів може змінюватися. Перед запуском перевірте парсер на реальному login-листі вашої скриньки; невідомий формат повертає «Новий код поки не знайдено», а не довільний код.

Джерела: [Gmail server-side authorization](https://developers.google.com/workspace/gmail/api/auth/web-server), [Google OAuth web-server flow](https://developers.google.com/identity/protocols/oauth2/web-server), [Gmail API](https://developers.google.com/workspace/gmail/api/reference/rest).

## Робота адміністратора

`/admin` доступна лише `ADMIN_ID` у приватному чаті; кожне admin-повідомлення та callback перевіряються на сервері. `/cancel` скасовує поточне введення. Чернетки автоматично закінчуються через 30 хвилин.

При додаванні введіть назву один раз, ціну, необов'язкові фото й опис, Steam login/password, за бажанням підключіть Gmail, оберіть показ на головній та підтвердьте preview. Одна назва й один опис показуються в обох мовних версіях інтерфейсу. Якщо Gmail пропущено, товар можна продавати, але кнопка «Отримати код» для нього не показується. Повідомлення з введеними Steam-паролями й Monobank-токеном бот намагається видалити з чату; у preview секрети не показуються.

Редагування назви й ціни не змінює історію. Steam credentials у старих покупках показуються актуальні з товару, щоб зміна пароля не залишала покупців із непрацюючими даними. Soft-deleted товари зберігаються для покупців.

Розсилка підтримує текст, фото з підписом і Telegram entities. Після preview потрібні два натискання підтвердження. Worker обмежує швидкість, обробляє блокування і `retry_after`, зберігає прогрес та надсилає підсумок. Після аварії між відправленням повідомлення і записом прогресу окремий адресат може отримати повтор розсилки.

У режимі технічних робіт нові замовлення не створюються, але оплачені покупки залишаються доступними. Статистика включає `paid` і `delivered`, суми збережені в копійках; «сьогодні» визначається за `TIMEZONE`.

## Видача і відновлення

Для платежів діє ідемпотентність у PostgreSQL і блокування рядка замовлення. Перед відправленням Steam-даних worker зберігає claim. Якщо Telegram міг прийняти повідомлення, але відповідь загубилась, неможливо гарантувати exactly-once між двома незалежними API. Таке замовлення залишається `paid`, позначається `delivery_uncertain`, автоматично повторно не надсилається; адміністратор отримує сповіщення. Покупець може відкрити дані через «Мої покупки». Завислий claim стає невизначеним через п'ять хвилин.

Повернення коштів і відкликання доступу після refund у цю версію не включено. Події reversal після успішної оплати не відкликають раніше видані дані.

## Резервні копії

Сервіс `backup` робить `pg_dump -Fc` щодня, зберігає 14 днів у `./backups`, обмежує права доступу. Копії містять персональні дані та зашифровані секрети. Використовуйте захищений диск і налаштуйте окреме шифроване offsite-сховище; локальний backup не захищає від втрати сервера. Ключ Fernet зберігайте окремо.

Перевіряйте дату останнього `.dump` і логи backup. Для навчального відновлення використовуйте **окрему порожню базу**, наприклад:

```sh
docker compose exec db createdb -U steamsell steamsell_restore_test
docker compose cp backups/FILE.dump db:/tmp/restore.dump
docker compose exec db pg_restore -U steamsell -d steamsell_restore_test --no-owner /tmp/restore.dump
```

Не запускайте destructive restore поверх робочої бази без перевіреної копії та плану зупинки сервісу.

Тести використовують SQLite та заглушки зовнішніх API. Вони перевіряють підписи, платежі, ідемпотентність, доступ, парсер, OAuth, Telegram routing та міграції. Вони не замінюють перевірку блокувань на PostgreSQL, Redis і реального циклу Telegram → тестовий Monobank → Gmail.

Перед прийманням на сервері пройдіть покупку у двох мовах, повтор webhook, неправильну суму, приховування купленого товару, перепідключення Gmail, блокування бота покупцем, перезапуск під час обробки платежу та відновлення backup в окрему базу.
